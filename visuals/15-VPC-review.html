15.1 deep dive Security Group vs NACL
The two firewall layers — they always confuse people. Here's the real difference.

🔵 Security Group — Instance level (stateful)

Attached directly to EC2. Has memory — remembers connections.
→ HTTP request comes IN ✅ (inbound rule allows it)
SG remembers this connection
← Response goes OUT ✅ automatically (no outbound rule needed!)
• Only Allow rules (no Deny)
• All rules evaluated together
• Default: all inbound denied, all outbound allowed

🟡 NACL — Subnet level (stateless)

Attached to the subnet. No memory — treats every packet independently.
→ HTTP request comes IN ✅ (inbound rule #100 allows it)
NACL forgets immediately
← Response tries to go OUT ❌ blocked! (needs explicit outbound rule)
• Both Allow and Deny rules
• Rules evaluated in number order (lowest first)
• Default: all traffic allowed
Security GroupNACL
LevelInstance (EC2)Subnet
Stateful?✅ Yes — return traffic auto-allowed❌ No — must allow both directions
Rule typesAllow onlyAllow AND Deny
Rule evaluationAll rules at onceIn order (lowest number first)
Block a specific IP?❌ Can't — no Deny rules✅ Yes — add a Deny rule
⚠️ Exam trap: "Block a malicious IP" → use NACL (has Deny). Security Groups can't block specific IPs.

• Works cross-account and cross-region

Few VPCs (2-3). For many VPCs → Transit Gateway.

15.5 VPC Endpoint Policies
JSON attached to the endpoint controlling what can pass through it.
3 security layers — all must allow
1️⃣ IAM Policy (user/role)
2️⃣ Endpoint Policy (on the endpoint)
3️⃣ Resource Policy (S3, SQS, etc.)
All 3 must allow → otherwise DENIED
