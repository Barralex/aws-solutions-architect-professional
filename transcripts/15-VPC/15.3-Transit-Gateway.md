# 15.3 - Transit Gateway

## Transcript

### Qué es
- Hub central para conectar miles de VPCs + on-premises (hub-and-spoke / star topology)
- Soluciona el problema de VPC Peering: SÍ tiene transitividad y edge-to-edge routing
- Recurso regional, pero se puede peer cross-region

### Features
- Conecta: VPCs, VPN, Direct Connect Gateway
- Compartir via RAM (Resource Access Manager) cross-account / dentro de Organization
- Route tables en el Transit Gateway para controlar qué habla con qué
- Soporte IP Multicast (único servicio en AWS que lo soporta)
- Cross-region peering entre Transit Gateways

### Edge-to-edge routing (lo que peering NO puede)
- Instancias en VPC pueden acceder via TGW a:
  - NAT Gateway en otra VPC
  - NLB en otra VPC
  - PrivateLink / EFS en otra VPC

### Arquitectura: NAT Gateway centralizado (Egress VPC)
- VPC Egress con NAT Gateway + IGW
- Otras VPCs (app1, app2) conectadas via Transit Gateway
- Route tables: 0.0.0.0/0 → TGW → VPC Egress → NAT GW → IGW
- Centraliza salida a internet, VPCs de apps se mantienen privadas
- TGW route tables controlan si las app VPCs pueden hablar entre sí o no

### Compartir via RAM
- Cuenta A crea TGW, lo comparte con Cuenta B via RAM
- Cuenta B acepta y puede crear VPC attachments al TGW
- Route tables separadas para aislar (prod vs staging vs dev)

### Multi-region
- Direct Connect Gateway puede conectar a TGW en múltiples regiones
- Inter-region peering entre Transit Gateways
- Intra-region peering mesh + inter-region peering mesh
- Billing: por hora por peering, sin cargos por procesamiento de datos

---

## Key Concepts
- TGW = hub central, transitivo, edge-to-edge routing (lo que peering NO tiene)
- Compartir con RAM cross-account
- Route tables en TGW para aislar ambientes (prod/staging/dev)
- IP Multicast = solo TGW
- NAT centralizado = Egress VPC + TGW
