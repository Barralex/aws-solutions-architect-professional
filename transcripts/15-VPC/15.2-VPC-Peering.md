# 15.2 - VPC Peering

## Transcript

### Qué es
- Conectar 2 VPCs de forma privada via red interna AWS
- Se comportan como si estuvieran en la misma red
- CIDRs NO pueden solaparse
- Funciona cross-region y cross-account

### Reglas clave
1. **No transitivo:** VPC A↔B y A↔C no significa B↔C. Hay que crear peering B↔C
2. **Actualizar route tables** en cada subnet de cada VPC
3. **Referenciar Security Groups** de VPC peered (cross-account también)

### Longest Prefix Match
- Ruta más específica (/32 > /16) tiene prioridad
- Permite enviar tráfico a IPs específicas por un peering y el resto por otro

### Configuraciones INVÁLIDAS
1. **CIDR overlap:** si CUALQUIER CIDR se solapa (IPv4 o IPv6) → no se puede peer
2. **No transitivo:** A↔B + A↔C ≠ B↔C
3. **No edge-to-edge routing:** VPC B peered con VPC A NO puede usar:
   - Internet Gateway de VPC A
   - NAT Gateway de VPC A
   - VPN/Direct Connect de VPC A
   - VPC Gateway Endpoints (S3, DynamoDB) de VPC A

### Configuración inválida típica del examen
- VPC central con NAT Gateway + IGW
- Otras VPCs peered queriendo salir a internet via VPC central
- ❌ NO FUNCIONA (no edge-to-edge routing)
- Solución: Transit Gateway (próxima lección)

---

## Key Concepts
- No transitivo, no edge-to-edge routing
- CIDR overlap = no peering
- Longest prefix match para routing
- NAT/IGW/VPN/DC NO se comparten via peering
