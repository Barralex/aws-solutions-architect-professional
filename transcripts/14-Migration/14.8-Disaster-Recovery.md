# 14.8 - Disaster Recovery

## Transcript

### RPO y RTO
- **RPO (Recovery Point Objective):** cuántos datos estás dispuesto a perder (frecuencia de backups)
- **RTO (Recovery Time Objective):** cuánto downtime es aceptable
- Menor RPO/RTO = más caro

### 4 Estrategias de DR (menor a mayor costo)
1. **Backup & Restore** - RPO/RTO alto, barato
2. **Pilot Light** - solo sistemas críticos corriendo (ej: DB)
3. **Warm Standby** - sistema completo corriendo a tamaño mínimo
4. **Multi Site / Hot Site** - producción completa en ambos sitios, activo-activo

### Backup & Restore
- Storage Gateway / Snowball → S3 → Glacier
- EBS Snapshots, RDS Snapshots programados
- RPO: horas/días. RTO: alto (recrear todo)
- Solo pagás almacenamiento

### Pilot Light
- DB crítica replicando continuamente (RDS)
- EC2 y demás NO corriendo
- En desastre: Route 53 failover + crear EC2
- RPO/RTO más bajo que B&R

### Warm Standby
- Sistema completo corriendo al mínimo (ELB + ASG mínimo + RDS)
- En desastre: Route 53 failover + auto-scale up
- Más caro pero failover rápido

### Multi Site / Hot Site
- Producción completa en ambos sitios
- Activo-activo con Route 53
- RTO: minutos/segundos
- Muy caro
- Cloud-only: Multi-Region con Aurora Global Database

### Tips DR
- Backups: EBS/RDS Snapshots → S3 → Glacier, CRR, Snowball/Storage Gateway
- HA: Route 53, RDS Multi-AZ, ElastiCache Multi-AZ, EFS, S3
- Network DR: Direct Connect + Site-to-Site VPN como backup
- Replicación: RDS Cross-Region, Aurora Global, Storage Gateway
- Automatización: CloudFormation, Beanstalk, CloudWatch Alarms, Lambda
- Chaos Testing: Netflix Simian Army, terminar instancias en producción

---

## Key Concepts
- RPO = pérdida de datos aceptable, RTO = downtime aceptable
- 4 estrategias: B&R < Pilot Light < Warm Standby < Multi Site
- Más bajo RPO/RTO = más caro
- Pilot Light = solo DB crítica corriendo
- Warm Standby = todo corriendo al mínimo
